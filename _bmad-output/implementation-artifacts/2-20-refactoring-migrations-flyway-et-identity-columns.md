# Story 2.20: Refactoring migrations Flyway et Identity Columns

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a **développeur**,
I want **des migrations conformes aux standards Flyway et utilisant les identity columns Oracle**,
so that **la gestion de schéma est robuste et les patterns sont modernes**.

## Acceptance Criteria

1. **AC1 — Convention de nommage Flyway**
   **Given** les fichiers de migration existants,
   **When** ils sont renommés selon la convention Flyway,
   **Then** le format est `V001__description_snake_case.sql` (double underscore entre version et description).

2. **AC2 — Suppression de SCHEMA_VERSION, utilisation de Flyway natif**
   **Given** la table custom `SCHEMA_VERSION` existe (V000),
   **When** le refactoring est terminé,
   **Then** la table `SCHEMA_VERSION` est supprimée et Flyway utilise sa table native `flyway_schema_history`.

3. **AC3 — Identity columns à la place des séquences**
   **Given** les tables utilisent des séquences pour les IDs,
   **When** les migrations sont refactorisées,
   **Then** toutes les colonnes ID concernées utilisent `GENERATED ALWAYS AS IDENTITY` (ou `GENERATED BY DEFAULT AS IDENTITY` si nécessaire pour migration de données),
   **And** les séquences existantes sont supprimées.

4. **AC4 — Tables impactées**
   Tables avec ID auto-généré à migrer : **USERS**, **ACTIONS_CATALOG**, **EXECUTION_LOG** (V006), **AUDIT_LOG**, **TAGS**, **PROFILES**.  
   USER_PERMISSIONS et ACTION_TAGS ont des clés composites ; pas de changement identity.  
   Si **USER_FAVORITES** existe déjà en migrations, l’inclure ; sinon à traiter lors de sa création (Story 3.1).

5. **AC5 — Backend et tests**
   **And** le code backend (repositories) est mis à jour pour ne plus référencer les séquences (aucun `NEXTVAL` explicite ; les repos utilisent déjà `INSERT...RETURNING ID`).
   **And** les tests unitaires et d’intégration passent avec les nouvelles migrations.
   **And** un script de migration de données est fourni si nécessaire (p.ex. env avec données existantes).

## Developer Context

### Technical Requirements

- **Flyway** : Utiliser Flyway (Community) CLI ou Maven. Support Oracle documenté (Oracle 18.4+, 26ai vérifiés). Pas d’Alembic.
- **Oracle** : `GENERATED ALWAYS AS IDENTITY` ou `GENERATED BY DEFAULT AS IDENTITY` (Oracle 12.1+). Project uses python-oracledb ; pas de changement driver.
- **Migrations** : Fichiers dans `idp-portal/database/migrations/`. Format `V{n}__description_snake_case.sql`. Flyway exécute en ordre de version.
- **Config** : URL JDBC Oracle (ou équivalent pour Flyway), utilisateur/mot de passe. Aligner avec `ORACLE_DSN`, `ORACLE_USER`, `ORACLE_PASSWORD` utilisés par le backend et les tests.

### Architecture Compliance

- **Structure** : Conserver `idp-portal/` (frontend, backend, database, scripts). Migrations dans `database/migrations/`. Architecture mentionnait scripts SQL versionnés + `SCHEMA_VERSION` ; cette story fait évoluer vers Flyway + `flyway_schema_history`.
- **Conventions** : Tables/colonnes UPPER_SNAKE_CASE, index `IDX_*`, contraintes `CK_*`/`UK_*`/`FK_*`. Conserver les noms de tables existants (USERS, ACTIONS_CATALOG, etc.).

### Library / Framework Requirements

- **Flyway** : Flyway Community (CLI ou Maven). Versions récentes supportent Oracle. Pas de dépendance Java dans l’app Python ; Flyway utilisé comme outil externe ou via wrapper.
- **Oracle** : Identity columns supportées depuis 12.1. Syntaxe standard : `ID NUMBER GENERATED ALWAYS AS IDENTITY` (ou `BY DEFAULT` si nécessité de fournir des IDs en migration).

## Dev Notes

- **Objectif** : Migrer vers un schéma de migrations standard (Flyway) et des patterns Oracle modernes (identity columns), tout en gardant le comportement fonctionnel et les tests verts.
- **Stratégie identity** : Sur base vide (ex. Docker dev), recréation des tables avec identity est simple. Sur base existante, prévoir migration de données et ordre des opérations (FK, etc.).
- **Repositories** : Ils utilisent `INSERT...RETURNING ID`. Aucun `NEXTVAL` explicite. Avec identity, le `RETURNING` reste valide ; rien à changer côté SQL des repos sauf si des tests mockent les séquences.
