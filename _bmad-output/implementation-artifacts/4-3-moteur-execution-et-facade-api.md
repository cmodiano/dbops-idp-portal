# Story 4.3: Moteur d'exécution et facade API

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a DBA,
I want que ma soumission d'exécution soit traitée par le backend qui orchestre automatiquement les étapes (Vault, plateforme, ServiceNow),
So that l'exécution se lance de manière fiable sans que je connaisse l'infrastructure sous-jacente.

## Acceptance Criteria

1. **AC1 — Création de l'exécution**
   **Given** un DBA confirme l'exécution au wizard,
   **When** le frontend envoie POST /api/v1/executions avec action_id, environment, parameters,
   **Then** le backend crée une entrée EXECUTIONS (statut "submitted") et les EXECUTION_STEPS correspondantes,
   **And** la réponse retourne HTTP 201 avec l'execution_id en < 3 secondes (NFR2).

2. **AC2 — Orchestration du moteur d'exécution**
   **Given** l'exécution est créée,
   **When** le moteur d'exécution démarre,
   **Then** il récupère les secrets nécessaires via le connecteur Vault (Story 4.2bis) en résolvant les credential_ref des intégrations (Story 2.27) — FR17, FR29,
   **And** il sélectionne l'adapter de plateforme correct (Strategy Pattern) selon la plateforme définie dans l'action,
   **And** il appelle adapter.trigger() avec les paramètres et les secrets.

3. **AC3 — Gestion indisponibilité Vault**
   **Given** Vault est indisponible,
   **When** le moteur tente de récupérer les secrets via le connecteur Vault,
   **Then** l'exécution est refusée avec un message explicite "Vault indisponible — exécution impossible" (NFR21),
   **And** le statut passe à "failed" avec la cause dans EXECUTION_STEPS.

4. **AC4 — Architecture et traçabilité**
   **And** les tables EXECUTIONS (V023, Story 4.1) et EXECUTION_STEPS (V025, Story 4.3) sont créées via migration SQL,
   **And** execution_repository.py encapsule le SQL brut pour les opérations CRUD,
   **And** le correlation ID est propagé dans tous les appels (Vault, plateforme, ServiceNow) — voir Task 3.3 pour génération, Task 4.3 pour propagation Vault, Task 4.5 pour propagation adapter,
   **And** FR18, FR17 et FR29 sont satisfaites.

## Dev Notes

### Contexte métier

- **FR17** : Le système récupère les secrets nécessaires depuis HashiCorp Vault au moment de l'exécution.
- **FR18** : Le système déclenche l'exécution sur la plateforme cible (AAP, GitHub Actions, Azure DevOps, Terraform) via une API.
- **FR29** : Le système ne stocke aucun credential — tous les secrets sont récupérés depuis Vault à l'exécution.
- **NFR2** : La soumission d'une exécution retourne en moins de 3 secondes (traitement asynchrone).
- **NFR21** : En cas d'indisponibilité de Vault, l'exécution est refusée avec un message explicite (pas de fallback).
- **Epic 4** : DBA exécute une action de bout en bout via le wizard et suit la progression étape par étape en temps réel via la timeline. Cette story 4.3 implémente le moteur d'exécution central qui orchestre Vault (4.2bis), intégrations (2.27), et adapters de plateforme (4.4+).

### Patterns à respecter

- **Repository Pattern** : SQL brut via python-oracledb dans execution_repository.py. Pattern établi dans catalog_repository.py, rbac_service.py. [Source: architecture.md, Story 2.1]
- **Strategy Pattern** : BaseAdapter interface avec trigger(), get_status(), parse_callback(). Factory function get_platform_adapter(platform). Pattern établi dans architecture.md pour extensibilité sans modifier le core. [Source: architecture.md]
- **Service Pattern** : ExecutionService orchestre l'exécution (Vault, adapter, ServiceNow). Injection via Depends. Pattern établi dans inventory_service.py (Story 4.2), vault_service.py (Story 4.2bis). [Source: architecture.md]
- **API** : REST JSON, snake_case, wrapper `{ "data": ... }` / `{ "error": ... }`, dates ISO 8601 UTC. [Source: architecture.md]
- **Erreurs** : Hiérarchie IdpError. VaultError (502), PlatformError (502), NotFoundError (404), ForbiddenError (403). Handler global dans main.py. [Source: architecture.md, exceptions.py]
- **Logging** : structlog JSON avec correlation_id propagé. `logger.info("execution_started", execution_id=..., correlation_id=...)`. [Source: architecture.md]

### Références techniques

- **Migration SQL** : Flyway avec scripts V{version}__{description}.sql. Séquences Oracle : `CREATE SEQUENCE SEQ_EXECUTIONS START WITH 1 INCREMENT BY 1`. Triggers auto-increment si besoin. CLOB pour JSON (parameters, output). [Source: architecture.md, migrations existantes V001-V022]
- **Repository** : python-oracledb 3.4.1 mode Thin. Pool connexions : `await pool.acquire()`. SQL brut avec paramètres bindés : `cursor.execute("INSERT INTO EXECUTIONS (...) VALUES (:1, :2, ...)", (val1, val2, ...))`. [Source: architecture.md, catalog_repository.py]
- **Strategy Pattern** : BaseAdapter ABC avec @abstractmethod. Factory : `_ADAPTER_REGISTRY = {"aap": AAPAdapter, "terraform": TerraformAdapter}`, `get_platform_adapter(platform) -> registry[platform]`. [Source: architecture.md, design patterns]
- **BackgroundTasks** : FastAPI BackgroundTasks.add_task(start_execution, execution_id) dans endpoint POST. Alternative : `asyncio.create_task(start_execution(execution_id))`. [Source: FastAPI docs]
- **Correlation ID** : UUID généré par endpoint, stocké dans structlog.contextvars : `structlog.contextvars.bind_contextvars(correlation_id=correlation_id)`. Propagé header X-Idp-Request-Id dans appels externes. [Source: architecture.md]

### Définition des étapes d'exécution

- **Structure EXECUTION_STEPS** : Chaque action définit ses étapes dans ACTIONS_CATALOG.EXECUTION_STEPS (CLOB JSON). Format : `[{"order": 1, "name": "Récupération secrets Vault", "type": "vault"}, {"order": 2, "name": "Ouverture changement ServiceNow", "type": "servicenow"}, {"order": 3, "name": "Exécution sur plateforme", "type": "platform"}, ...]`.
- **Mapping étapes → implémentation** : type "vault" → vault_service.get_secret(), type "servicenow" → servicenow_service.create_change() (Story 4.5), type "platform" → adapter.trigger() (Story 4.4). Le moteur itère sur les étapes et exécute chaque type.
- **Gestion erreurs par étape** : Si une étape échoue → update step status "failed" + error_message. Exécution globale passe en status "failed". Étapes suivantes sont skippées (status "skipped").

### Latest Tech Information

- **FastAPI BackgroundTasks** : `background_tasks.add_task(func, *args)` exécute func après retour réponse HTTP. Limitation : si process crash, tâche perdue. Alternative : asyncio.create_task() ou task queue (Celery/ARQ) pour production (Phase 2). [Source: FastAPI docs]
- **python-oracledb 3.4.1** : Mode Thin (pas de client Oracle), async natif. Pool : `await pool.acquire()` → connexion. `cursor.execute()` avec bind variables. CLOB : `cursor.var(oracledb.DB_TYPE_CLOB)`. [Source: python-oracledb docs]
- **ABC Strategy Pattern** : `from abc import ABC, abstractmethod`. Classe BaseAdapter(ABC) avec @abstractmethod pour trigger(), get_status(), parse_callback(). Subclasses doivent implémenter toutes les méthodes abstraites. [Source: Python ABC docs]
- **structlog correlation ID** : `structlog.contextvars.bind_contextvars(correlation_id=...)` lie le correlation_id au contexte thread/async. Tous les logs suivants incluent automatiquement correlation_id. `clear_contextvars()` pour nettoyer. [Source: structlog docs]
